Time Tracker — Design Document

Personal work-time tracking & analysis · CLI-first, web/phone-later · 2026-06-28

1. Context & Goals

The aim is to honestly understand how work time is spent and to become more efficient. Calendar meetings form a fixed scaffold; the real question is what happens in the gaps between meetings. Inspired by stint-tracker, a Python CLI that gamifies focused "stints".

Goals (MVP):

  • See where time goes (honest accounting across categories of work).
  • Reflect on output (what was actually accomplished vs time spent).
  • Reduce idle / fragmented gaps between meetings.

Deferred goal: deep-work motivation via gamification/rewards (see Future Work).

2. Core Design Insight

Don't build three trackers. Build one canonical timeline of TimeEntry records, and treat the live timer, periodic check-in, retrospective backfill, and calendar import as four input paths that all write the same shape. Every entry carries a source field. This makes "do all three capture modes" sensible, makes backfill trivial, and keeps the door open for a web/phone front-end (it just reads/writes the same store).
┌─ live timer ───┐ ├─ check-in ─────┤ ┌──────────────┐ ┌── CLI views (now) calendar ──►├─ backfill ─────┼────► │ TimeEntry │ ────►├── analysis/reports sync └────────────────┘ │ timeline │ └── web/phone (later) └──────────────┘

5. Notifications & Reminders (macOS)

A CLI only acts while running. To notify when the app is closed, two pieces combine:

  1. Scheduling — a launchd LaunchAgent (plist in ~/Library/LaunchAgents/), reliable on macOS and reboot-safe. One agent fires the daily clock-in reminder at a configurable time; another fires periodic check-ins on an interval.
  2. Display — native banners via terminal-notifier (fallback osascript -e 'display notification').

tt install-reminders writes the plists for you; tt uninstall-reminders removes them. Each agent invokes a small tt subcommand that fires the banner, nudging you to run tt in or tt checkin.

6. Google Calendar OAuth Setup

  1. Go to Google Cloud Console → create/select a project.
  2. Enable the Google Calendar API for that project.
  3. Configure the OAuth consent screen (External, add your own email as a test user).
  4. Create an OAuth Client ID of type Desktop app; download credentials.json.
  5. Place it at ~/.time_tracker/credentials.json.
  6. Run tt sync — first run opens a browser for consent; the token is cached at ~/.time_tracker/token.json and auto-refreshes after.
  7. Setup lists upcoming events with their colors so you confirm pink = colorId 4 (some calendars may use a different id) before locking in excluded_color_ids.

7. Build Phases & Test Plan

Tests are written and run after each phase using pytest against an in-memory SQLite DB; the suite must stay green before moving on.

  • Phase 1 — Core & Storage MVP
    db.py, models.py (schema + migrations, TimeEntry CRUD), config.py.
    Tests: schema creation; entry create/read/update/delete; running-entry (null end_ts) handling; config load/save defaults; timestamp ordering & timezone correctness.
  • Phase 2 — Capture (3 modes) MVP
    core/timer.py (start/stop), core/checkin.py, core/backfill.py (fill gaps against the day timeline).
    Tests: timer start creates open entry & stop closes it; cannot start two timers at once; check-in writes a point/interval entry; backfill detects gaps correctly and rejects overlaps with existing entries/meetings.
  • Phase 3 — Calendar Sync MVP
    core/gcal.py: OAuth, pull events with color_id/event_type, filter excluded colors.
    Tests (mocked Google API): event parsing into calendar_event; excluded colorId filtering; idempotent re-sync (no duplicates); all-day & cross-midnight event handling; token refresh path.
  • Phase 4 — Workday & Reminders MVP
    core/workday.py (clock in/out + inference fallback), core/notify.py, tt install-reminders.
    Tests: manual clock in/out persists one row/day; inference picks correct first/last activity; LaunchAgent plist generated with correct schedule/paths; notify command builds the right shell invocation (mocked).
  • Phase 5 — CLI Front-end MVP
    cli.py (typer): in/out, start/stop, checkin, day, sync, report, install-reminders.
    Tests: Typer CliRunner smoke tests for each command (exit code 0, expected output); end-to-end on a temp DB exercising all three capture modes + day view.
  • Phase 6 — Analysis MVP
    core/reports.py: time-by-category, meeting vs focus vs idle, fragmentation metric, workday-length trend.
    Tests: aggregation totals match seeded fixtures; idle = workday − meetings − entries; fragmentation metric on known timelines; empty-day & overlapping-entry edge cases.

8. Future Work

Future Gamification / rewards — stint-tracker-style streaks, minimum-duration "stints", milestone treats, layered over the same timeline.

Future Web & phone — FastAPI wrapper over core/ → responsive web UI / PWA.

Future Phone geofencing — automatic arrive/leave detection at the work location (the real replacement for Maps Timeline).

Future Takeout Timeline importer — optional batch backfill of location-based workday bounds from a Google Takeout JSON export.

Future Screenshot calendar import — vision-based extraction as a fallback to the live API.

9. Verification (end-to-end)

  • Unit tests (above) green after every phase via pytest.
  • Manual run: create entries via all three modes, tt sync against a real calendar, confirm tt day shows meetings (pink excluded) + logged time + gaps, and tt report week aggregates sanely.
  • Read the same DB from a throwaway script to prove core/ is front-end-agnostic for the future web app.
